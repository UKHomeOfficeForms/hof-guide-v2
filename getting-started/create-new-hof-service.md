# Create a new HOF service

## Purpose

This tutorial shows you how to create a new Home Office Forms service from an empty folder.

Use this page instead of copying a separate skeleton repository. The guide is the source of truth for the current recommended starting point.

By the end, you will have a working HOF service with:

- one form page
- validation
- translations
- a check answers page
- a confirmation page
- Redis-backed sessions for local development
- scripts for running, building and testing the service

## Key concepts

A minimal HOF service has four main parts:

| Part | What it does |
| --- | --- |
| `server.js` | Starts HOF and registers one or more form apps. |
| `apps/<app-name>/index.js` | Defines the route journey: steps, fields, behaviours and next pages. |
| `apps/<app-name>/fields.js` | Defines field-level validation and field configuration. |
| `apps/<app-name>/translations/src/en/*.json` | Defines the text shown to users, split by HOF translation namespace. |

HOF also needs a session store. Use Redis locally unless your service has a specific test-only setup.

The current analysed HOF framework version is `hof@24.5.0`. New services should target Node.js `>=24.15.0`.

## Usage guidance

Use this tutorial when you are starting a new HOF service and want to understand every file you add.

Do not start by copying `hof-skeleton` unless your team has explicitly decided to maintain it as a separate product dependency. A skeleton repository can become outdated, insecure or misleading if it is not kept in step with HOF.

For a new service, prefer this approach:

1. create an empty repository
2. install HOF directly
3. add the smallest working route journey
4. run it locally
5. add features as the service needs them

## Examples

This example builds a service called `permit-application`.

### Step 1: Create the project

```bash
mkdir permit-application
cd permit-application
yarn init -y
yarn add hof
```

### Step 2: Add a useful `.gitignore`

Create `.gitignore`:

```text
node_modules/
.env
.DS_Store
yarn-error.log*
```

Commit an example environment file, but do not commit real local secrets.

### Step 3: Update `package.json`

Replace the generated scripts and add the Node.js requirement:

```json
{
  "name": "permit-application",
  "version": "0.1.0",
  "private": true,
  "description": "Permit application built with Home Office Forms",
  "scripts": {
    "start": "node server.js",
    "build": "hof-build",
    "dev": "hof-build watch --env .env",
    "test": "echo \"Add service tests\""
  },
  "engines": {
    "node": ">=24.15.0"
  },
  "dependencies": {
    "hof": "^24.5.0"
  }
}
```

The `hof` package provides the `hof-build` command.

Use `yarn start` for a built service. Use `yarn dev` during development so translations and assets are rebuilt when files change and local `.env` is passed to the server.

### Step 4: Create the folder structure

Create this structure:

```text
permit-application/
  server.js
  package.json
  .env.example
  apps/
    permit/
      index.js
      fields.js
      translations/
        src/
          en/
            journey.json
            pages.json
            fields.json
            validation.json
  behaviours/
  models/
  assets/
    js/
      index.js
    scss/
      app.scss
```

You do not need custom behaviours, models or assets on day one, but creating the folders gives the service a clear place to grow.

### Step 5: Add local environment values

Create `.env.example`:

```bash
NODE_ENV=development
PORT=8080
REDIS_HOST=127.0.0.1
REDIS_PORT=6379
REDIS_DOCKER_PLATFORM=
SESSION_SECRET=12345678901234567890123456789012
```

Create a local `.env` from it:

```bash
cp .env.example .env
```

For real services, replace `SESSION_SECRET` with a secret generated by your secret-management process. It must be exactly 32 bytes.

### Step 6: Add `server.js`

Create `server.js`:

```js
'use strict';

const hof = require('hof');
const permit = require('./apps/permit');

hof({
  root: __dirname,
  appName: 'Permit application',
  routes: [permit]
});
```

This starts HOF, sets the project root, names the app and registers the `permit` route journey.

### Step 7: Add your first route journey

Create `apps/permit/index.js`:

```js
'use strict';

const Summary = require('hof').components.summary;

module.exports = {
  name: 'permit',
  baseUrl: '/',
  fields: 'apps/permit/fields',
  translations: 'apps/permit/translations',
  steps: {
    '/name': {
      fields: ['full-name'],
      next: '/contact'
    },
    '/contact': {
      fields: ['email-address'],
      next: '/confirm'
    },
    '/confirm': {
      behaviours: [Summary, 'complete'],
      sections: {
        applicant: ['full-name', 'email-address']
      },
      next: '/confirmation'
    },
    '/confirmation': {
      backLink: false
    }
  }
};
```

This journey has:

- `/name` for the applicant name
- `/contact` for the applicant email address
- `/confirm` for check answers
- `/confirmation` for the final page

The `Summary` component builds the check answers page. The string behaviour `'complete'` marks the journey complete before the confirmation step.

### Step 8: Add fields and validation

Create `apps/permit/fields.js`:

```js
'use strict';

module.exports = {
  'full-name': {
    validate: [
      'required',
      { type: 'maxlength', arguments: 200 }
    ]
  },
  'email-address': {
    validate: [
      'required',
      'email'
    ]
  }
};
```

Fields are reusable. A field appears on a page when the step includes its key in the `fields` array.

### Step 9: Add translations

Create `apps/permit/translations/src/en/journey.json`:

```json
{
  "header": "Permit application",
  "serviceName": "Permit application",
  "confirmation": {
    "message": "Application successful",
    "details": "Your application has been submitted."
  }
}
```

Create `apps/permit/translations/src/en/pages.json`:

```json
{
  "name": {
    "header": "What is your full name?",
    "title": "What is your full name?"
  },
  "contact": {
    "header": "What is your email address?",
    "title": "What is your email address?"
  },
  "confirm": {
    "header": "Check your answers",
    "title": "Check your answers",
    "sections": {
      "applicant": {
        "header": "Applicant details"
      }
    },
    "fields": {
      "full-name": {
        "label": "Full name"
      },
      "email-address": {
        "label": "Email address"
      }
    }
  },
  "confirmation": {
    "header": "Application complete",
    "title": "Application complete"
  }
}
```

Create `apps/permit/translations/src/en/fields.json`:

```json
{
  "full-name": {
    "label": "Full name"
  },
  "email-address": {
    "label": "Email address"
  }
}
```

Create `apps/permit/translations/src/en/validation.json`:

```json
{
  "full-name": {
    "required": "Enter your full name",
    "maxlength": "Full name must be 200 characters or fewer"
  },
  "email-address": {
    "required": "Enter your email address",
    "email": "Enter an email address in the correct format, like name@example.com"
  },
  "default": "Enter a valid value"
}
```

HOF separates journey configuration from page text. `hof-build` compiles these source files into `apps/permit/translations/en/default.json` with top-level `fields`, `validation`, `pages` and `journey` keys.

The route `translations` setting points to the translations directory, not a JSON file pattern. HOF appends `/__lng__/__ns__.json` internally. Do not set `translations` to `apps/permit/translations/__lng__/__ns__.json`, because HOF will append the pattern again and translation lookups will render placeholder keys such as `fields.full-name.label`.

Do not put all translation content in `translations/src/en/default.json`; that creates a nested `default.*` namespace and HOF will also render placeholder keys.

### Step 10: Add minimal frontend assets

Create `assets/js/index.js`:

```js
'use strict';
```

Create `assets/scss/app.scss`:

```scss
@import "hof/frontend/themes/gov-uk/styles/govuk";
```

If your service does not need custom frontend behaviour yet, keep these files minimal.

### Step 11: Start Redis

HOF uses Redis-backed sessions by default.

If you already have Redis running locally, use it. Otherwise, add `docker-compose.yaml`:

```yaml
services:
  redis:
    image: redis:7-alpine
    platform: ${REDIS_DOCKER_PLATFORM:-}
    ports:
      - "6379:6379"
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5
```

Start Redis:

```bash
docker compose up -d redis
docker compose exec redis redis-cli ping
```

The `ping` command should return `PONG`. Leave Redis running while you develop the service.

Keep `REDIS_DOCKER_PLATFORM` empty unless Docker is forcing an incompatible image platform. On Apple Silicon, if your shell or Docker Desktop sets `DOCKER_DEFAULT_PLATFORM=linux/amd64`, Redis can run through qemu emulation and crash when HOF checks the connection. In that case set `REDIS_DOCKER_PLATFORM=linux/arm64/v8` in `.env`, then recreate Redis.

### Step 12: Build and run the service

In another terminal, build translations and frontend assets:

```bash
yarn build
```

Start the development service:

```bash
yarn dev
```

Open:

```text
http://localhost:8080/name
```

You should be able to:

1. enter a name
2. enter an email address
3. check your answers
4. continue to the confirmation page

### Step 13: Use watch mode while developing

During development, use:

```bash
yarn dev
```

This runs HOF's watch task using your `.env` file.

Use this when changing:

- routes
- fields
- translations
- frontend assets

### Step 14: Add tests before production use

The tutorial uses a placeholder test script so the first app is easy to understand.

Before a real service goes live, add tests for:

- route configuration
- validation
- conditional routing
- behaviours
- submission integrations
- important accessibility journeys

## Common issues

### The app starts but pages show missing text

Run:

```bash
yarn build
```

Then restart the app. Missing page text usually means translations have not been built or the route `translations` path is wrong.

### Labels render as placeholder keys

If the page shows text such as `journey.header`, `fields.full-name.label` or `pages.confirm.sections.applicant.header`, HOF could not find the translation key.

Check the route points to the translations directory:

```js
translations: 'apps/permit/translations'
```

Do not include `__lng__` or `__ns__` in the route setting. HOF adds those placeholders internally.

Then rebuild translations and restart the service:

```bash
yarn build
yarn dev
```

### HOF cannot find field configuration

Check the route has the right field path:

```js
fields: 'apps/permit/fields'
```

Also check the field key in the step matches the key in `fields.js`.

### The service fails because `SESSION_SECRET` is invalid

`SESSION_SECRET` must be exactly 32 bytes. Placeholder values such as `changethis` are not valid.

### The service fails because 'SESSION_SECRET' is 'missing'

`Error: Session secret is required. Set the SESSION_SECRET environment variable to a 32-byte value.` 

Run the service using `yarn dev` rather than `yarn start` - this ensures your local `.env` is passed correctly.

### Pages do not retain values between requests

Check Redis is running and that `REDIS_HOST` and `REDIS_PORT` point to the Redis instance your app can reach.

### Redis logs `UNCERTAIN_STATE` for command `INFO`

HOF's Redis client sends the Redis `INFO` command as part of its connection ready check. If the app logs `UNCERTAIN_STATE` for `INFO` immediately after `Connected to redis`, first check whether the Redis container is healthy:

```bash
docker compose logs redis
docker compose exec redis redis-cli ping
```

If the Redis logs include `qemu: uncaught target signal 11`, the Redis image is running under an incompatible emulation platform. On Apple Silicon, set the Compose platform override in `.env`:

```bash
REDIS_DOCKER_PLATFORM=linux/arm64/v8
```

Then recreate Redis and check it responds:

```bash
docker compose down
docker compose up -d redis
docker compose exec redis redis-cli ping
```

### The journey skips or loops unexpectedly

Check each step's `next` value. Every non-terminal form step should point to another configured step.

### You copied an old skeleton service and it behaves differently

Treat old skeleton repositories as historical examples only. Check the HOF version, Node.js requirement, session settings, dependencies and route patterns against this guide.
